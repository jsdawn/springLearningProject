# P0 鉴权闭环：下游服务接入网关透传

## 目标
承接阶段 网关 JWT 鉴权，让下游 `user / product / order` 业务代码能直接拿到登录用户身份，且未登录请求统一返回 401。

## 现状摸底（开始前）
- `common-core/.../context/` 已存在基础组件：
  - `LoginUser` 实体（userId / username / jti）
  - `LoginUserHolder` ThreadLocal 封装（set/get/clear）
  - `LoginUserContextFilter` 用 `@Component` + `OncePerRequestFilter`，请求开始从 `X-Auth-*` 写上下文，请求结束 clear
- 三个业务服务都依赖 `common-core`，Filter 自动生效，**无需手动注册拦截器**
- 网关层 `JwtAuthGlobalFilter` 已经透传 `X-Auth-UserId / X-Auth-Username / X-Auth-Jti`
- `common-auth.AuthConstants` 已定义 Header 常量

## 实际改动

### 1. `common-core` 新增 `UnauthorizedException`
继承 RuntimeException，标记未登录/登录已失效场景。由 `LoginUserHolder.require()` 抛出。

### 2. `LoginUserHolder` 扩展 3 个方法
- `require()`：返回 LoginUser，空时抛 UnauthorizedException
- `requireUserId()`：返回 userId 字符串
- `requireUserIdAsLong()`：返回 userId Long（数据库主键），无法解析抛 IllegalStateException

### 3. `GlobalExceptionHandler` 新增 401 处理器
```java
@ExceptionHandler(UnauthorizedException.class)
public ApiResponse<Void> handleUnauthorizedException(UnauthorizedException e) {
    return ApiResponse.fail(401, e.getMessage());
}
```

### 4. `OrderServiceImpl.createOrder` 接入上下文
- 移除 `validateCreateRequest` 里 `userId is required` 的硬编码校验
- `createOrder` 方法入口处调用 `request.setUserId(LoginUserHolder.requireUserIdAsLong())`
- 强制用登录用户覆盖客户端传的 userId，**堵住伪造身份下单的安全漏洞**

### 5. MQ 延时消息自动正确
`OrderDelayMessage.userId` 从 `OrderInfo.userId` 来，而 OrderInfo.userId 已被上下文覆盖，无需额外改动。

## 验证清单（Apifox）

| 场景 | 步骤 | 期望 |
|---|---|---|
| 登录后正常下单 | 登录拿 Token → 调用 `/orders` POST | 200，订单 user_id = 当前登录用户 |
| 未登录访问业务 | 不带 Token 直接 POST `/orders`（绕过网关） | 401，code=401，message="未登录或登录已失效" |
| 伪造 X-Auth-UserId | 带 Token，Header 加 `X-Auth-UserId: 999` | 网关清洗后下游拿到的是真实 userId，订单 user_id ≠ 999 |
| Token 注销后访问 | 把 Token 加入 Redis 黑名单 → 调业务 | 网关 401 |

## 设计要点

### 为什么用 Filter 而非 Interceptor
- `OncePerRequestFilter` 在 Servlet 容器层介入，比 Spring MVC 的 `HandlerInterceptor` 更早，所有请求都会经过
- 写在 `common-core` 里用 `@Component` 自动注册，三个业务服务依赖即生效，**避免了在每个服务重复注册拦截器的样板代码**

### 为什么在 Service 层覆盖 userId 而不是 Controller
- 单一职责：Service 是业务逻辑的边界，Controller 只负责协议层
- 防止未来新增 Controller 接口时遗漏鉴权检查
- MQ 消息、生产事件、审计日志都能自动用上正确的 userId

### 为什么不直接删除 CreateOrderRequest.userId
- 遵守项目约束「不修改原有接口，优先新增接口」
- 保留字段保持 API 兼容性，客户端调用方式不变；但业务层强制覆盖，客户端传的 userId 永远不生效

## 待办（不在 P0 范围）
- `OrderController.list / page / detail / cancel`：目前仍接受 userId 参数作为查询条件，未做"只能查自己订单"的权限校验——属于 P4 业务优化「简易角色权限控制」
- `product-service` 创建/修改商品、`user-service` 用户中心等接口：同上，可在 P4 阶段统一处理

## 学到的踩坑
- 不要重复造轮子：动手前先 grep 现有代码，common-core 早就有了基础组件
- 客户端鉴权不能"软信任"：客户端传的 userId 永远要当成"建议值"，必须用上下文强制覆盖
- 401 是协议级错误码：放在 GlobalExceptionHandler 统一处理，业务代码只管抛 UnauthorizedException
