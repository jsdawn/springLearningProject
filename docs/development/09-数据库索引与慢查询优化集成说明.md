# P3 数据库专项（一）：索引优化与查询演进

## 目标

解决单库 `mall_db` 的两类索引问题：该联合的不该拆散、该有的列不存在。核心方法论是**索引服务于查询**——先让业务查询存在，再为它建索引，而不是照着规划文档凭空建。

## 现状摸底（开始前）

原计划是"补齐索引：`order.user_id+status`、`product.category_id`"。摸底后发现两个假设都要修正：

1. **orders 已有两个单列索引** `idx_orders_user_id`、`idx_orders_status`，且查询里（`OrderMapper.xml` 的三个条件查询）**根本没有 status 条件**——直接建 `(user_id, status)` 联合索引没有查询路径可用，EXPLAIN 无从验证。正确顺序是先给分页接口加 status 筛选（业务演进），再上联合索引。
2. **products 表没有 category_id 列**——"按分类查商品"要的是先加列，加索引只是顺手的事。
3. `idx_orders_status`、`idx_products_status` 都是**低基数单列索引**（分别只有 3、2 个取值），优化器几乎不会选中，属于"看起来建了、实际没用"的冗余索引。
4. `orders` 仅 31 行，EXPLAIN 前后对比看不出差别——需要造数到万级才有说服力。

## 实际改动

### 1. 订单分页接口新增 status 筛选

- `OrderPageQuery` 新增 `status` 字段（`@Min(1) @Max(3)`，可空）
- `OrderMapper.xml` 三处 `<where>` 补 `AND status = #{status}` 条件

这样新增了两个真实查询路径：`WHERE user_id=? AND status=?`（"我的待支付订单"）和 `WHERE status=?`。

### 2. orders 联合索引替换两个单列索引

```sql
ALTER TABLE orders
    ADD INDEX idx_orders_user_status (user_id, status),
    DROP INDEX idx_orders_user_id,
    DROP INDEX idx_orders_status;
```

为什么敢删：`WHERE user_id=?` 走联合索引**左前缀**，单列 `idx_orders_user_id` 的活它全包了；`ORDER BY id LIMIT` 也无需 filesort（见设计要点）；status 单列索引无人使用。

### 3. products 分类演进

- `products` 表新增 `category_id BIGINT DEFAULT NULL` + 索引 `idx_products_category`，删除 `idx_products_status`
- `Product` 实体（兼任创建/更新请求体）、`ProductPageQuery`、`ProductMapper.xml`（SELECT 列、where 条件、INSERT、UPDATE）同步加 `categoryId`

### 4. schema.sql 与迁移脚本的分工

**`CREATE TABLE IF NOT EXISTS` 对已存在的表完全不生效**——改 `schema.sql` 里的建表语句不影响现有 mall_db。所以本项目采用双轨：

- `schema.sql`：只保证**新环境**（删库重建、别人 clone 后首次启动）拿到最终表结构
- 各服务 `src/main/resources/db/migration/V<n>__描述.sql`：**已有库**执行一次的 ALTER 迁移（本项目惯例：按服务归属拆分，order 侧 `V3__orders_composite_index_user_status.sql`，product 侧 `V2__products_add_category_id.sql`）

这就是最简单的"迁移"概念：学习项目没有引入 Flyway，但 schema 变更已经有"新装"与"存量"两条路径，Flyway 解决的正是把这个过程自动化、版本化的问题（后续可作选修）。

### 5. 造数脚本

`docs/sql/p3-seed-data.sql` 用 `WITH RECURSIVE` 给 orders 造 1 万行（`ORDSEED` 前缀，user_id/status 轮转分布）、products 造 200 行；`p3-seed-cleanup.sql` 按前缀清理，不碰业务数据。

注意 MySQL 的递归 CTE 默认深度上限 1000，造 1 万行前必须 `SET SESSION cte_max_recursion_depth = 1000000`，否则中途报错。

## EXPLAIN 验证用例

前置：执行 `p3-migration.sql` + `p3-seed-data.sql`。逐条跑 `EXPLAIN`，关注 `type / key / rows / Extra`。

| # | SQL | 优化前期望 | 优化后期望 |
| --- | --- | --- | --- |
| 1 | `EXPLAIN SELECT * FROM orders WHERE user_id=1 AND status=1` | key=`idx_orders_user_id`，status 只能回表后过滤 | key=`idx_orders_user_status`，两列都在索引内过滤 |
| 2 | `EXPLAIN SELECT * FROM orders WHERE user_id=1 ORDER BY id LIMIT 10` | key=`idx_orders_user_id`，无 filesort | key=`idx_orders_user_status`（走左前缀），依然无 filesort——验证删单列索引不伤原查询 |
| 3 | `EXPLAIN SELECT id, status FROM orders WHERE user_id=1 AND status=1` | 回表 | `Using index`（覆盖索引：查询列全在联合索引里） |
| 4 | `EXPLAIN SELECT * FROM orders WHERE order_no LIKE '%SEED%'` | type=ALL（左通配，索引失效） | （不变，这就是结论本身；对照 `LIKE 'ORDSEED%'` 为 range） |
| 5 | `EXPLAIN SELECT * FROM products WHERE category_id=5` | type=ALL | type=ref，key=`idx_products_category` |
| 6 | `EXPLAIN SELECT * FROM orders WHERE user_id=1 ORDER BY id LIMIT 10 OFFSET 9900` | — | rows 依然小但 OFFSET 深分页真实扫描量大，引出待办 |

用例 4 的价值在于**证明什么优化做不了**：左通配 LIKE 无法走 B+ 树索引，方案是改前缀匹配、全文索引或搜索引擎，本阶段只记录不动手。

## 设计要点

### 最左前缀原则决定索引形状

联合索引 `(user_id, status)` 是按 user_id 排序、user_id 相同再按 status 排序的 B+ 树。`WHERE status=1` 单独出现用不上它；`WHERE user_id=?` 单独出现用得上（左前缀）。建联合索引前先列出查询模式，把**等值条件放前面**。

### ORDER BY id 为什么天然无 filesort

InnoDB 二级索引的叶子节点隐式携带主键，所以 `idx_orders_user_status` 实际是 `(user_id, status, id)` 有序结构。`WHERE user_id=?` 命中后同 user_id 的行按 (status, id) 有序，即使 SQL 里只按 id 排，优化器也能利用索引顺序（配合 LIMIT 时尤为明显）。这也是"删掉单列索引不伤 ORDER BY"的原因。

### 低基数索引是负资产

status 只有 2~3 个取值，单列索引的选择性极差（扫 1/3 的行不如全表扫），优化器基本不会选它，但它仍占空间、拖慢写入。判断标准不是"字段会不会被查"而是"查询模式 + 选择性"，将来真有 `WHERE status=?` 的高频查询，正确形状是 `(status, xxx)` 组合而非单列。

### LIKE 的左通配与索引

`LIKE 'ORD2026%'` 可走索引（range），`LIKE '%2026'` 不能——B+ 树按前缀有序，前缀未知就只能全扫。`order_no LIKE CONCAT('%', ? , '%')` 的两头通配写法在现有查询里就是全表扫描，数据量上去后是第一个要优化的点。

### MyBatis 动态 SQL 参数三处必须同步（本次踩坑）

给分页查询新增过滤条件时，要改的是**三处**，缺一处就会在运行时炸：

| 位置 | 本次改动 |
| --- | --- |
| 查询 DTO | `OrderPageQuery.status`、`ProductPageQuery.categoryId` |
| Mapper XML | `<if test="status != null">` / `<if test="categoryId != null">` |
| **Mapper 接口** | `@Param("status")` / `@Param("categoryId")` |
| **Service 调用点** | 把 DTO 里的字段取出来传给 Mapper |

典型报错：`BindingException: Parameter 'categoryId' not found. Available parameters are [keyword, param1]`——MyBatis 只暴露接口上声明过的 `@Param`。

**关键教训**：javac 编译**抓不到**这类问题。XML 与接口的一致性靠运行时反射校验，Java 侧签名（接口、Service 调用）能编译通过是因为参数类型碰巧兼容（少传一个引用类型 / 顺序错位都合法）。所以索引类改动除了编译，**必须真正调一次接口**才算验证。本项目可用一条巡检兜底：比对每个 Mapper XML 里 `<if test="...">` 用到的变量与接口 `@Param` 的并集。

### updateById 全字段覆盖的坑

`Product` 实体兼任请求体后，`updateById` 会把 `category_id` 无条件覆盖为请求值——**更新商品时若不带 categoryId，已有分类会被置 NULL**。这是沿用"全字段覆盖"接口语义的一致代价（remark 等字段同款问题）。生产做法是动态 SET 或 DTO 分离，此处先记录。
