# 角色权限控制（RBAC）集成说明（阶段12 · 上）

> 对应学习路线阶段12（P4 业务优化第一部分）。前置：阶段7 JWT 网关鉴权（`X-Auth-*` Header 透传链路已就位）。  
> 涉及服务：user-service / gateway-service / common-auth / common-core / product-service / order-service。

## 目标

本项目的接口全部服务于管理台，需要按管理台社区规范实现「用户 → 角色 → 权限」三层解耦的 RBAC 权限控制：接口的访问门槛由**权限点**决定，改角色授权只改数据库绑定、不改代码。

## 为什么不是"角色开关"

第一版尝试把角色硬编码在 `users.user_type`（1 管理员 / 2 普通），接口上用 `@RequireRole("ADMIN")` 判断。这只能算「角色开关」，有两个硬伤：

1. **角色是代码里的常量**：加一个角色、调整某接口允许哪些角色，都要改代码重新发版
2. **权限关系隐含在注解里**：「ADMIN 能调哪些接口」散落在各 Controller 的注解参数上，无法在数据库/管理界面统一管理

RBAC 把「用户—角色—权限」拆成三个独立实体，权限是数据库里的一等公民（`sys_permission` 表），角色与权限的绑定（`sys_role_permission`）可随时增删，全程不改代码。这也是 RuoYi 等管理后台的标准模型（RuoYi 的 `sys_menu.perms` 字段就是权限点，`@ss.hasPermi('system:user:remove')` 校验的就是这个串）。

## 数据模型（四张表）

| 表                     | 作用                         | 关键字段                       |
| ---------------------- | ---------------------------- | ------------------------------ |
| `sys_role`             | 角色                         | `role_code`（JWT 中的角色值）      |
| `sys_permission`       | 权限点                       | `perm_code`（注解校验的值）        |
| `sys_user_role`        | 用户—角色绑定                | `user_id` + `role_id`           |
| `sys_role_permission`  | 角色—权限绑定                | `role_id` + `permission_id`     |

- DDL 在 `user-service/schema.sql`（新环境自动建表）+ `db/migration/V4__add_rbac.sql`（已有库增量，纯 DDL）
- 种子数据（2 角色 + 10 权限点 + 绑定）在 `user-service/data.sql`，`INSERT IGNORE` 幂等，靠四张表的唯一键防重

**10 个权限点**（编码规范：`模块:动作`，与 Controller 注解一一对应）：

| 模块   | 权限点                                                       |
| ------ | ------------------------------------------------------------ |
| 用户管理 | `users:list` `users:page` `users:detail` `users:create` `users:update` `users:status` |
| 商品管理 | `products:create` `products:update` `products:status` `products:stock` |

种子绑定：`admin` → ADMIN 角色（绑全部权限点）；`alice` → USER 角色（不绑权限点，只能走查询和下单这类「仅需登录」的行为）。

## 鉴权链路

```
登录(AuthServiceImpl)
  └─ 查角色集合(findRoleCodesByUsername) + 权限集合(findPermCodesByUsername)
       └─ 写进 JWT claims: roles=[...], perms=[...]
            └─ 网关(JwtAuthGlobalFilter) 校验 token 后透传
                 X-Auth-Roles / X-Auth-Perms（同时清理客户端伪造的同名头）
                   └─ 下游 LoginUserContextFilter 读头 → LoginUser 挂 roles/perms 集合
                        └─ @RequirePermission("xxx") + RoleCheckAspect 切面
                             在方法进入前校验：未登录 401 / 权限不足 403
```

## 设计要点

**1. 权限校验为什么打在 Controller（管理台规范）**  
本项目接口都是管理台功能，权限本质是「这个角色能不能调这个功能」的粗粒度准入，与数据归属、业务状态无关。这类校验用注解声明式打在 Controller 最合适，对齐 RuoYi 的 `@PreAuthorize("@ss.hasPermi(...)")` 惯例。机制上 `@RequirePermission` + AOP 与 Spring Security `@PreAuthorize` 同源（都是注解 + AOP 自动代理），以后迁 Security 只换注解名。数据归属类业务规则（只能操作自己的订单）仍留 Service 层，覆盖 MQ 消费者、内部 Feign 等非 HTTP 入口。

**2. 权限集合放 JWT（无状态）的取舍**  
角色/权限写进 JWT claims，下游拿到 Header 即可本地校验，无需每次查库或查 Redis，网关也无需转发到 user-service 鉴权。代价是**改授权要重新登录才生效**（旧 token 里还是老集合）。RuoYi 把权限放会话/Redis，是即时生效；学习期选 JWT 无状态方案，文档在此记录这个权衡。

**3. 内部接口必须拆分**  
`POST /products/{id}/stock` 原本被「管理台补货」和「Feign 下单扣库存」共用，直接加 `products:stock` 权限会拦断下单链路。因此拆出 `/internal` 内部接口：管理台端点要权限、内部端点不设权限门槛。**关键认知：Feign 是服务发现直连调用，不经网关、不带 `X-Auth-*` 头**，会原样撞上下游服务的权限校验。凡服务间内部调用一律走 `/internal` 路径。

**4. 内部接口的安全边界（学习期 vs 生产）**  
`/internal` 接口在本项目里靠「约定不暴露给前端 + 路径不对外公布」隔离，经网关仍可被直接访问。生产环境必须补一道边界：网关路由层拦截 `/internal/**`（只允许来自内网/服务间），或叠加服务间调用凭证（如内部 token / mTLS），否则内部接口就是没有权限门的后门。

**5. 权限点编码规范**  
统一 `模块:动作` 三段式（如 `users:create`、`products:stock`），`sys_permission.perm_code` 与 Controller 注解字符串严格一致。加新接口时：先定义权限点 → 入库种子 → 注解标注，三步同步，避免注解引用了不存在的权限点导致「无人能访问」。

## 验证清单（自测用）

前置：执行 `V4__add_rbac.sql` 建表 + 执行 `data.sql` 的 RBAC 种子（或 `INSERT IGNORE` 部分）。

| 用例 | 预期 |
| ---- | ---- |
| 无 token → `GET /users/page` | 401 |
| admin token → `GET /users/page`、`POST /products` | 200 |
| alice token → `GET /users/page`、`POST /products` | 403（无 users:page / products:create） |
| alice 伪造 `X-Auth-Perms: users:page` 头 | 仍 403（网关清掉伪造头） |
| alice token → `GET /products/{id}` | 200（查询接口开放，供商城/Feign） |
| admin / alice 下单 `POST /orders` | 200 且库存扣减（验证 Feign 走 `/internal` 内部接口） |
| 升级前签发的旧 token → 管理接口 | 403（旧 token 无 roles/perms claim） |

## 踩坑

- **给接口加权限前，先 grep 所有 `@FeignClient` 的调用路径**：服务间 Feign 调用不带网关注入的 `X-Auth-*` 头，会被下游权限校验误拦成 401「未登录或登录已失效」。本次就漏了 `order-service` 下单时 Feign 调 `user-service /users/{id}` 这条链路，接口加 `users:detail` 权限后下单被拦——凡服务间调用一律拆 `/internal` 接口。
- **查询接口别一刀切加权限**：`product` 的 list/page/detail 保持开放，因为商城展示和下单链路 Feign 调 detail 都要走；只对写接口加权限点。
- **权限点编码和注解字符串必须逐字符一致**：不一致时 `hasAnyPermission` 判空，表现为「有权限但 403」，排查方向容易跑偏。
- **`data.sql` 种子与 `data-locations: []` 的冲突**：`application.yml` 里 `data-locations: []` 会禁用 `data.sql` 自动执行（历史原因是 admin/alice 用普通 INSERT 非幂等），因此 RBAC 种子用 `INSERT IGNORE` 幂等化后仍需手动执行进库。
