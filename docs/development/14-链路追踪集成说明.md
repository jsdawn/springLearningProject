# 阶段13｜链路追踪集成说明（Sleuth + Zipkin）

> 所属阶段：阶段13 P5 可观测性（第一部分）。第二部分 Prometheus + Grafana（指标监控）另篇。
> 前置：阶段12③ 日志规范（统一 pattern 含 `%X{traceId}`）——本篇的 Sleuth 会自动接管 traceId 的生成与 MDC 写入。

## 一、要解决的问题

阶段12③ 的手工 traceId 方案（网关生成 → Filter 写 MDC → Feign 透传）能回答「这次请求动了哪些服务」（grep 同一 traceId），但回答不了：

- **每一段耗时多少、卡在哪一跳**（下单慢，是 order 本身慢还是 Feign 扣库存慢？）
- **调用拓扑**（谁调用了 product？扇出关系长什么样？）
- **span 级父子层级**（一次请求内部的分段计时）

Sleuth + Zipkin 把「traceId 从日志串起来」升级为「span 树 + 耗时瀑布图」。

## 二、角色分工

| 组件 | 形态 | 职责 |
|---|---|---|
| **Sleuth 3.1.5** | jar 依赖（进服务进程） | 自动埋点：HTTP 请求、Feign 调用、定时任务等生成 traceId/spanId；跨进程透传；耗时计入 span；traceId 自动写 MDC |
| **Zipkin Server** | 独立容器（`openzipkin/zipkin`，9411） | 收集各服务异步批量上报的 span，存储并提供 Web UI（瀑布图/拓扑图/依赖图） |

版本来源：父 pom 已托管 `spring-cloud-dependencies 2021.0.5`，Sleuth 由该 BOM 管理为 **3.1.5**，子模块引 starter **无需写版本号**。Zipkin 镜像 3.0 与之兼容（上报走 Zipkin v2 JSON API）。

## 三、落地步骤

### 1. docker-compose 加 zipkin 容器（dev-env-docker）

```yaml
zipkin:
  image: openzipkin/zipkin:${ZIPKIN_VERSION:-3.0}
  environment:
    TZ: Asia/Shanghai
  ports:
    - "${ZIPKIN_PORT:-9411}:9411"
```

- 学习期用默认**内存存储**（重启数据清空）；生产换 elasticsearch/mysql
- ⚠️ 拉镜像踩坑：Docker Desktop 未配 HTTPS 代理时直连 docker.io 超时，走国内镜像源拉取后打标签：
  `docker pull docker.m.daocloud.io/openzipkin/zipkin:3.0 && docker tag ... openzipkin/zipkin:3.0`
- UI 地址：http://localhost:9411/zipkin

### 2. 四个服务加依赖（pom）

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-sleuth</artifactId>
</dependency>
<!-- starter-sleuth 已含 brave 埋点核心，此处只加 Zipkin 上报器 -->
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-sleuth-zipkin</artifactId>
</dependency>
```

gateway-service（WebFlux）同样适用——Sleuth 对 WebFlux/Reactor 有专门 instrumentation。

### 3. 四个服务加配置（application.yml，本地文件）

```yaml
spring:
  sleuth:
    sampler:
      # 采样率 1.0 = 全采样（学习环境抓全量；生产一般 0.01~0.1）
      probability: 1.0
  zipkin:
    base-url: ${ZIPKIN_BASE_URL:http://localhost:9411}
```

**配置归属**：上报地址与采样率是环境连接信息，按项目惯例留本地 yml 不进 Nacos。

## 四、设计要点

### 1. 与阶段12③ 手工 traceId 的关系：接管 + 瘦身，不是并存

Sleuth 启用后自动生成 traceId、跨服务传播（b3 头）、写 MDC（键名同为 `traceId`），现有日志 pattern `%X{traceId}` 原样工作。**手工链路随之清理**，不能两套并存——否则网关出现两个独立 traceId 源（UUID 手工版 vs Sleuth 版），下游 MDC 被 Sleuth 覆盖，响应头回传值与日志值不一致，报障时对不上。

| 手工件 | 处置 | 说明 |
|---|---|---|
| TraceIdFilter 的 traceId 生成/读头/写 MDC | ❌ 删除 | Sleuth 全覆盖（含直连端口场景） |
| TraceIdFilter 的 userId 写 MDC | ✅ 保留 | Sleuth 不管用户标识，拆成 `UserIdMdcFilter`；finally 只 `remove` 自己的 key（`MDC.clear()` 会误伤 Sleuth 写入的 span 信息） |
| 网关 TraceIdGlobalFilter 生成/透传 X-Trace-Id | ❌ 删除 | 消除双 traceId 源，统一走 b3 |
| 网关响应头回传 X-Trace-Id | ⚠️ 改造保留 | 改从 Sleuth `Tracer.currentSpan()` 取值，保证响应头/日志/Zipkin 三者同源；order 用 `HIGHEST_PRECEDENCE + 10` 落在 Sleuth 埋点过滤器（+5）之内才能取到 span |
| Feign 手工透传 X-Trace-Id | ❌ 删除 | Sleuth 的 Feign instrumentation 自动传播 b3 |
| 网关请求日志手工拼 traceId | ❌ 删除 | Sleuth 3.x 自动装饰 Reactor 链传播 MDC，pattern 里的占位符对网关日志同样生效 |

### 2. 上报是异步批量的

Sleuth 通过 `zipkin-reporter` **异步批量**（队列攒批 + 后台线程）POST 到 Zipkin，业务请求不等待上报完成——对接口 RT 几乎零影响；服务崩溃时丢最近一批 span（可接受）。

### 3. 采样率是"入口决策"

采样在**链路入口**（gateway）决定，traceId 头里带采样标记，下游全部遵循——不在每个服务各自掷骰子，保证一条链要么全采要么全丢。

### 4. 数据流全景

```
gateway/order/user/product（Sleuth 埋点，span 进内存队列）
        │ 异步批量 HTTP POST（v2 JSON）
        ▼
Zipkin Server (9411)：收集 → 存储（学习期内存）→ Web UI
        ▼
瀑布图：按 trace 查询，看每跳耗时/父子层级；依赖图：服务拓扑
```

### 5. 排障入口约定

- 看「一段请求发生了什么」：Zipkin UI 按 service 名 / 时间过滤 → 点开 trace 看瀑布
- 看「日志细节」：从 Zipkin trace 详情复制 traceId → 回各服务日志 grep
- 两者以 traceId 关联，Zipkin 详情页也直接展示各 span 的 tag

## 五、踩坑与注意

1. **Sleuth 版本别写死**：由 spring-cloud-dependencies BOM 托管（2021.0.5 → Sleuth 3.1.5），子模块只写 groupId:artifactId
2. **starter-sleuth 与 sleuth-zipkin 是两个依赖**：前者只埋点不上报（traceId 只进日志不进 Zipkin）；后者才是上报通道，缺一不可
3. **采样率默认 0.1**：不加配置时 10 条链路只留 1 条，测试时"怎么查不到刚下的单"多半是这个——学习期显式设 1.0
4. **Zipkin 3.0 镜像 Java 17 运行**，与客户端 JDK 8 无关（客户端只发 HTTP），版本无耦合
5. **内存存储重启即空**：查历史链路前先确认容器没重启过
6. **容器内无法反查宿主服务**：上报方向是「服务(宿主) → Zipkin(容器 9411 映射端口)」，单向出站，无 Seata 那样的 IP 注册回连问题

## 六、验证方法

1. `docker compose up -d zipkin`，健康检查 `GET http://localhost:9411/health` 返回 200
2. 服务启动日志出现 `The [order-service] service will be publishing to Zipkin` 字样
3. 走网关下一单（触发 order→user/product Feign 链）
4. `GET http://localhost:9411/zipkin/api/v2/traces?serviceName=order-service&limit=5` 应出现含 3 个服务 span 的完整 trace
5. UI 瀑布图检查：gateway → order → (user, product) 父子层级正确、各段耗时合理
