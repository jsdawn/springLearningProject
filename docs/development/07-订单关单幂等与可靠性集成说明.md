# P2 订单关单链路：幂等与可靠性

## 目标

解决超时关单链路的两个可靠性缺口：

1. **库存泄漏**：订单已关闭（状态 1→3）但库存回补失败时，旧实现把异常吞掉，消息照常 ACK，这部分库存在系统里永久丢失且没有任何报错
2. **无限重投**：消费失败后 `basicNack(requeue=true)` 没有次数上限，下游长时间不可用时消息会无限循环重投

## 现状摸底（开始前）

先说结论：**关单的幂等其实已经做好了，不需要重做**。

`closeExpiredOrder` 用的是条件更新做乐观锁：

```java
int rows = orderMapper.updateStatusFromTo(id, ORDER_STATUS_CREATED, ORDER_STATUS_TIMEOUT_CLOSED);
if (rows <= 0) {
    return false;   // 已不是待支付，幂等跳过
}
```

对应 SQL 语义是 `UPDATE orders SET status=3 WHERE id=? AND status=1`。这是原子的 check-and-set：消息重投第二次时状态已是 3，影响行数为 0，直接跳过，**不会重复回补库存**。并发的两条消息同时到达时，数据库行锁也保证只有一个能更新成功。

所以本次不动幂等机制，只补上面那两个真正的缺口。

## 实际改动

### 1. `closeExpiredOrder` 纳入 Seata 全局事务

```java
@Override
@GlobalTransactional(name = "close-expired-order", rollbackFor = Exception.class)
@Transactional
public boolean closeExpiredOrder(Long id) {
```

两个注解的职责与下单链路一致：`@GlobalTransactional` 是 TM（申请 XID、经 Feign 传给 product-service），`@Transactional` 是本地分支边界。

这样"订单状态改为超时关闭"与"库存回补"成为一个原子操作。回补失败 → 全局回滚 → 订单退回待支付 → 消息重投再试，不会出现关了单却没还库存的中间态。

### 2. `rollbackStockForItems` 不再吞噬异常

```java
private void rollbackStockForItems(List<OrderItem> items) {
    if (items == null || items.isEmpty()) {
        return;
    }
    for (OrderItem item : items) {
        adjustProductStock(item.getProductId(), item.getQuantity());
    }
}
```

去掉了原来包裹每一条的 `try-catch`。这是本次最关键的一处：**吞掉的异常正是全局事务的触发信号**，不让它冒泡，`@GlobalTransactional` 就永远不知道该回滚。

旧实现"尽力而为"的注释是站在"没有分布式事务"的前提下的，现在前提变了，策略必须跟着变。

### 3. 死信消费者加消费重试上限

`OrderDeadLetterConsumer` 新增两个常量与两个私有方法：

- `MAX_RETRY_COUNT = 3`：重试上限
- `RETRY_COUNT_HEADER = "x-retry-count"`：重试计数存放的消息头

处理失败的分支改为：读计数 → 已达上限则 ACK 丢弃并打 ERROR 告警 → 未达上限则**重新发布一条携带 `计数+1` 的消息到死信交换机**，再 ACK 原消息。

重新发布失败（Broker 不可用）时退回 `basicNack` 重投兜底，绝不在这种情况下 ACK，避免消息丢失。

## 验证清单

前置：`order-service`、`product-service`、RabbitMQ 正常运行。测试接口见 `OrderMqTestController`。

| 场景             | 步骤                                                                                          | 期望                                                              |
| -------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 正常关单           | 下单 → `POST /order-mq-test/delay/{orderId}?ttlSeconds=15` → 15 秒后查订单                             | `status=3`，商品库存已回补                                                |
| 幂等跳过           | `POST /order-mq-test/delay-mock?orderId=999999&ttlSeconds=10`                                | 日志出现 `[MQ-DLQ] 订单无需关闭（不存在或非待支付状态），幂等跳过`                         |
| 重复消费幂等         | 对同一订单连发 2 条 15 秒延时消息                                                                         | 第一条关单回补，第二条幂等跳过；**库存只回补一次**（不会翻倍）                               |
| **全局回滚（关键）**  | ① 正常下单（库存已扣）② 停掉 `product-service` ③ 发 15 秒延时消息 ④ 15 秒后查订单                                   | 订单 `status` 仍为 **1**（未被关闭）；日志出现 `安排第 N 次重试`                     |

第四个用例是本次的核心验证：如果订单状态变成了 3 而库存没回补，说明全局事务没生效。

## 设计要点

### 为什么回补失败必须冒泡

分布式事务里，**静默的成功比失败更危险**。旧实现吞掉异常后，系统呈现出的状态是"关单成功、没有任何报错"，但库存凭空少了一份。这类问题在线上往往几周后才被对账发现，届时早已无法追溯。

让异常冒泡之后，失败是**显式**的：订单退回待支付、消息重投、日志告警，任一环节都能观测到。

### 为什么不用 `basicNack(requeue=true)` 做重试

`nack` 只能把消息原样塞回队列，**改不了消息头**，重试次数无从记录，结果是"要么无限重投、要么永远不知道重试了几次"。

改成"重新发布携带计数的新消息 + ACK 旧的"后，计数随消息头传递，才能判断何时该放弃。

重新发布的目标是**死信交换机**而不是延时队列——发到延时队列会重新计时 30 分钟，重试就失去了意义。

### 已知权衡：幂等跳过也会开一次空全局事务

`@GlobalTransactional` 在方法入口就向 TC 申请 XID，所以"订单不存在""已支付"这些幂等跳过的分支也会走一次完整的 begin + commit，多一次 TC 往返。

优化方向是把全局事务下移到"确认需要关单"之后的内部方法，但那需要拆方法且必须走代理调用（同类内部调用不触发 AOP），复杂度明显上升。考虑到超时关单消息到达时订单通常确实是待支付（30 分钟未支付才触发），跳过分支占比不高，这里接受该开销。

## 待办

- 重试达上限后目前只打 ERROR 日志，生产环境应把消息转入独立的"异常归档队列"由人工介入
- 下单接口幂等（重复点击 / 网关重试导致重复下单）尚未处理，属于 P2 的另一半
- `order-service` 目前没有接 Redis，若后续要做下单幂等 token 需要先引入

## 踩坑记录

- **别在 `@GlobalTransactional` 方法里吞异常**：这是最容易踩的坑，吞掉之后注解形同虚设，且不报任何错
- **Seata 全局事务不挑入口**：MQ 消费者线程里同样可以开启，XID 在事务开始时新建并绑定到当前线程，经 Feign 拦截器传给下游，与 HTTP 入口无差别
- **重新发布消息要新建 `MessageProperties`**：原消息属性里带着消费端特有的 `deliveryTag`、消费时间戳等，原样转发出去语义混乱，只保留内容类型与持久化设置即可
