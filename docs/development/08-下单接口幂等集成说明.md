# P2 下单接口幂等：幂等 token 机制

## 目标

防止重复下单：用户连点提交按钮、网络超时后客户端自动重试、网关/代理层重发请求——这些都会让同一个"下单意图"到达 `POST /orders` 多次。下单是**创建**语义，没有现成的幂等保护，重复提交的后果是两笔真实订单 + 双倍扣库存，这不是重试能容忍的错误。

## 现状摸底（开始前）

`createOrder` 无任何幂等机制：每次 POST 都真实落库。07 篇的关单幂等（`UPDATE orders SET status=3 WHERE id=? AND status=1` 条件更新）在这里**不适用**——条件更新幂等的前提是"行已存在"，而 INSERT 没有可复用的状态位。

可替代方案对比：

| 方案 | 思路 | 不选它的原因 |
| --- | --- | --- |
| 数据库唯一键 | 客户端生成 requestId，表加唯一索引，重复插入报错回滚 | 冲突发生在数据库层，异常路径绕过了正常业务流；且无效请求已完整走完事务，浪费资源 |
| **幂等 token（本次采用）** | 先领一次性令牌，提交时原子消费 | 重复请求在**进入业务之前**就被拦下，代价是多一次领号请求 |

token 方案的额外前提：order-service 需要一个能做"原子 check-and-delete"的存储。此前 order-service 没接 Redis（07 待办里记了一笔），本次先补上。

## 实际改动

### 1. order-service 接入 Redis

`pom.xml` 新增两个依赖（版本均由 parent 2.7.18 托管）：

- `spring-boot-starter-data-redis`：默认 Lettuce 客户端
- `commons-pool2`：Lettuce 连接池依赖，**不引入时 yml 里的 `lettuce.pool` 配置会被静默忽略**（退化为单连接模式），且不报任何错

`application.yml` 新增（注意前缀是 **`spring.redis.*`**，Spring Boot 3.x 才改为 `spring.data.redis.*`）：

```yaml
spring:
  redis:
    host: ${REDIS_HOST:localhost}
    port: ${REDIS_PORT:6379}
    timeout: 3000ms
    lettuce:
      pool:
        max-active: 8
        max-idle: 8
        min-idle: 0
```

### 2. `DuplicateSubmitException` + 409 映射

common-core 新增 `DuplicateSubmitException`（与 `UnauthorizedException` 并列、同风格），`GlobalExceptionHandler` 新增映射：

```java
@ExceptionHandler(DuplicateSubmitException.class)
public ApiResponse<Void> handleDuplicateSubmitException(DuplicateSubmitException e) {
    return ApiResponse.fail(409, e.getMessage());
}
```

409 Conflict 是"请求与资源当前状态冲突"的标准语义，比 400/429 更贴切。

### 3. `IdempotentTokenService`（核心）

两个动作，一领一销：

- **下发**：UUID → `SET order:idempotent:token:<uuid> "1" EX 300`，5 分钟过期
- **消费**：Lua 脚本原子"存在即删"——键存在则 DEL 返回 1（放行），否则返回 0（抛 `DuplicateSubmitException`）

```java
private static final DefaultRedisScript<Long> CONSUME_SCRIPT = new DefaultRedisScript<>(
        "if redis.call('GET', KEYS[1]) then "
                + "return redis.call('DEL', KEYS[1]) "
                + "else "
                + "return 0 "
                + "end",
        Long.class);
```

**为什么必须用 Lua 而不是 GET + DEL 两步**：两步之间存在时间窗口，两个并发请求可能都 GET 到令牌、又都执行 DEL，双双放行，幂等失效。Lua 脚本在 Redis 单线程内整体执行，天然原子。

**为什么不用 GETDEL 命令**：`GETDEL` 是 Redis 6.2+ 才有的命令，本环境 Redis 是 5.0.14，Lua 是唯一原子做法。

`DefaultRedisScript` 作为静态常量只解析一次，Spring 会缓存脚本 SHA1 实际走 EVALSHA，避免每次全量传输脚本。

### 4. `OrderController` 改造

```java
@GetMapping("/idempotent-token")
public ApiResponse<String> issueIdempotentToken() {
    return ApiResponse.success("Idempotent token issued", idempotentTokenService.issueToken());
}

@PostMapping
public ApiResponse<OrderInfo> create(@Valid @RequestBody CreateOrderRequest request,
                                     @RequestHeader(value = "X-Idempotent-Token", required = false) String idempotentToken) {
    // 第一关：令牌必须携带，缺失 → IllegalArgumentException → 400
    if (!StringUtils.hasText(idempotentToken)) { throw new IllegalArgumentException(...); }
    // 第二关：原子消费，重复/过期 → 409
    idempotentTokenService.consumeToken(idempotentToken);
    // 之后才走原有下单业务
    OrderInfo createdOrder = orderService.createOrder(request);
    ...
}
```

注意 `required = false`：**缺失和无效分开处理**。缺失用 400（客户端没走流程），无效用 409（流程走了一半），排障时一眼可分。

## 验证清单

前置：重启 order-service（新依赖生效）；Redis、MySQL、网关正常；持有有效登录 token（经网关调用，所有 `/orders/**` 需鉴权）。

| 场景 | 步骤 | 期望 |
| --- | --- | --- |
| 领令牌 | `GET /orders/idempotent-token`（带 Authorization） | 返回 UUID 令牌 |
| 正常下单 | `POST /orders`，请求头带 `X-Idempotent-Token: <令牌>`，body 含占位 userId | 下单成功，库存扣减 |
| **重复提交（核心）** | 同一令牌**再发一次**相同请求 | `409`，订单不重复创建、**库存不二次扣减** |
| 缺少令牌 | `POST /orders` 不带请求头 | `400`，提示先领号 |
| 过期令牌 | 领令牌后等 5 分钟再提交 | `409`（验证 TTL 可临时调小 `TOKEN_TTL`） |
| 伪造令牌 | 随便编一个 UUID 当令牌 | `409` |
| 并发竞争（可选） | 两个终端同时用同一令牌下单 | 恰好一单成功，另一单 409 |

第 7 个用例是 Lua 原子性的直接验证：若两单都成功，说明消费动作不是原子的。

## 设计要点

### 为什么消费必须在下单业务之前

先消费后下单，才能保证并发请求只有一个能通过闸门——若先下单后消费，两个并发请求可能都完成下单，消费动作形同虚设。

但这带来一个**已知权衡**：令牌消费成功后，若 `createOrder` 因业务原因失败（如库存不足），令牌已经被烧掉，客户端用同一令牌重试会收到 409。生产做法是前端在收到**业务失败**（区别于 409）后自动重新领号重试；学习项目先在 Controller 注释里记录该行为。

### 两层幂等的分工

- **token 幂等（本篇）**：挡在门口，防"同一意图到达多次"（连点、重试）
- **条件更新幂等（07 篇）**：数据库兜底，防"已经进来的重复"（MQ 消息重投、超时关单二次触发）

两者作用在不同的入口上，不互相替代。如果哪天 token 机制本身出 bug，条件更新仍能保证关单链路不重复回补库存。

### 令牌要不要绑定用户

当前 key 只有 UUID（熵足够、不可猜测），未绑定 userId。生产收紧方式是把 key 改为 `order:idempotent:token:<userId>:<uuid>`，消费时用当前登录用户的 userId 拼 key——顺带解决"用户 A 拿用户 B 的令牌提交"这类理论攻击面。留作待办。

## 待办

- 令牌绑定 userId（见上）
- Redis 不可用时的降级策略：当前 Redis 挂掉会让下单直接 500（fail-closed，安全但不可用）；需权衡是否接受 fail-open（放行重复风险）
- 前端约定：业务失败自动重新领号；409 时提示用户而非自动重试

## 踩坑记录

- **Spring Boot 2.7 的 Redis 前缀是 `spring.redis.*`**，不是 3.x 的 `spring.data.redis.*`。照抄新教程配置在本项目里会静默连不上
- **Redis 5.0 没有 `GETDEL`**（6.2+ 才有），网上"原子取删"教程用 GETDEL 的，在这里只能改写 Lua
- **不加 `commons-pool2` 时 Lettuce 连接池配置静默失效**：单连接模式下 yml 的 pool 配置不报错、不生效，性能问题要到压测才暴露
- **脚本直调下单接口现在必须先领令牌**：旧测试脚本直接 POST 会得到 400。另外 07 篇的占位 `userId` 坑依旧存在——`@NotNull` 校验在 Controller 层先于 Service 层覆盖执行
