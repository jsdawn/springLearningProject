# 深分页优化集成说明（阶段11 · 上）

> 对应学习路线阶段11（P3 数据库专项第二部分）。前置：阶段10 索引优化（`(user_id, status)` 联合索引已就位）。  
> 涉及服务：order-service。

## 目标

分页接口在数据量增大后，`LIMIT #{size} OFFSET #{offset}` 的页深与扫描成本成正比（第 1 页与第 9000 页耗时相差几个数量级）。本篇用两种方案解决，并说明各自的适用边界：

1. **延迟关联（子查询定位 id）**：优化现有 `GET /orders/page` 的大偏移场景，对调用方透明
2. **游标分页（lastId 续拉）**：新增 `GET /orders/page/cursor`，翻页成本恒定，彻底消除偏移量

## 问题本质

`LIMIT 20 OFFSET 90000` 的真实语义是：**取出 90020 行整行，组装好，再丢弃前 90000 行**。两个成本来源：

- 扫描 90020 行（这个没法省，偏移量必须逐行数出来）
- 每行都按 `SELECT *` 组装整行数据（这个可以省——90 万行里只有最后 20 行是真正需要的）

## 方案一：延迟关联

```sql
SELECT o.id, o.order_no, ...
FROM orders o
INNER JOIN (
    SELECT id
    FROM orders
    WHERE ...
    ORDER BY id
    LIMIT #{size} OFFSET #{offset}
) t ON o.id = t.id
ORDER BY o.id
```

内层子查询只需要 `id` 一列——主键就在二级索引叶子节点上，**纯覆盖索引扫描**，"数偏移量"这一步不再组装任何整行。内层只交出一个起点，外层按主键精确回表 20 次。

注意：本例 `ORDER BY id` 恰好在聚簇索引上，回表本身不贵；**延迟关联收益最大的场景是按二级索引排序**（如 `ORDER BY create_time`），朴素写法要为被丢弃的每行做一次随机 I/O 回表，延迟关联把回表从 N 次降到 size 次。

## 方案二：游标分页

```sql
SELECT ... FROM orders
WHERE id > #{lastId} ...
ORDER BY id
LIMIT #{size}
```

以上一页最后一条记录的 id 为游标，B+ 树直接定位后续拉。**任意页成本恒定 O(size)**，第 1 页和第 90000 页一样快。

```java
// 探测下一页的技巧：按 pageSize + 1 查询，多查的一条丢弃。
// 返回条数超过 pageSize 即 hasMore=true，省去单独的 COUNT 或第二趟查询。
List<OrderInfo> fetched = orderMapper.findPageByCursor(..., pageSize + 1);
boolean hasMore = fetched.size() > pageSize;
if (hasMore) {
    fetched = fetched.subList(0, pageSize);
}
```

返回结构 `CursorPageResult`：不返回 total/pages，改为 `nextCursor`（本页最后一条的 id）+ `hasMore`。游标模式下持续写入的数据总数随时在变，total 本身语义不稳，跳页也不成立。

## 设计要点

**1. 为什么用阈值切换而不是全量替换延迟关联？**  
小偏移（前几十页）时两种写法成本相当，延迟关联还多一次 join 开销。`DEEP_PAGE_OFFSET_THRESHOLD = 1000`：小偏移走简单写法，大偏移才付出 join 的复杂度。这也是"不要为优化而优化"的落地形式。

**2. 两种方案怎么选？**

|          | 延迟关联               | 游标分页          |
| -------- | ------------------ | ------------- |
| 跳页       | ✅ 支持               | ❌ 只能顺序翻       |
| 页深增大     | 变慢（但比朴素 LIMIT 好得多） | 恒定 O(size)    |
| 返回 total | ✅                  | ❌（语义不稳）       |
| 前端交互     | 传统页码               | "加载更多" / 无限滚动 |
| 改造成本     | 对调用方透明             | 前后端都要配合改      |

电商"我的订单"这类无限滚动场景用游标；管理后台要跳页用延迟关联 + 阈值。

**3. `<sql>` 片段的 AND 前缀技巧**  
共享片段里每个 `<if>` 都以 `AND` 开头，放进 `<where>` 时首项的 AND 会被 `<where>` 自动剥离——这样同一片段既能单独构成条件块，也能与额外条件（游标的 `id > #{lastId}`）拼接，一处维护多处复用。

**4. 游标列的选择**  
必须选**有序且稳定**的列（自增主键 id 最合适）。若用 create_time 做游标，同秒多条记录会造成漏读/重读；且游标列上要有索引。本例 id 主键天然满足。

## 验证清单（自测用）

前置：执行 `docs/sql/p3-seed-data.sql` 造 1 万行订单。

1. `GET /orders/page?pageNum=1&pageSize=20` → 走原路径，行为不变
2. `GET /orders/page?pageNum=500&pageSize=20`（offset=9980 ≥ 阈值）→ 自动走延迟关联，返回结果与朴素 LIMIT 完全一致
3. `GET /orders/page/cursor` → 从头拉第一页，记下 `nextCursor`
4. `GET /orders/page/cursor?lastId=<nextCursor>` → 正确续拉，无重复无遗漏
5. 连续续拉到 `hasMore=false`，累计条数应等于该过滤条件的总数（可与 `/orders/page` 的 total 互验）
6. 带过滤条件的游标分页：`/orders/page/cursor?userId=1&status=1&lastId=...` → 条件生效
7. EXPLAIN 对比：`LIMIT 9000,20` 朴素 vs 延迟关联（内层 rows/Extra 变化）vs 游标（rows≈21）

## 踩坑

- **`<include>` 与 `<where>` 嵌套**：`<where>` 剥离 AND 只发生在**直接子内容**的开头，片段内第一个 `<if>` 不命中时会继续剥第二个的 AND——所以片段每项都带 AND 是安全的；但若把 `<include>` 放在子查询里（本篇延迟关联内层），外面包一层 `<where>` 再剥，不要依赖外层
- **游标分页别再查 COUNT**：返回 total 会把恒定成本变回线性扫描，`hasMore` 用 size+1 探测就够了
- **MyBatis 四件套教训延续**：新增两个 Mapper 方法的 XML、接口、Service 调用点、参数命名必须一次同步齐（阶段10 踩过 BindingException）
