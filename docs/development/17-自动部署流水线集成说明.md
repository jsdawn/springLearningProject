# 17 - 自动部署流水线集成说明（GHCR → SSH 生产自动部署）

> 阶段14 P6 收官。在 15（CI + 串行门禁）、16（闭环部署演练）基础上，把"手动 SSH 上服务器
> pull + up -d"这一步交给流水线：**push main → CI 测试 → build-push 推 GHCR → deploy job
> SSH 到生产 pull + up -d + 冒烟检查**，全链路无人值守。数据库迁移脚本仍手动执行，不在自动链路内。

## 一、方案设计

### 1.1 流水线全景

```
git push main
    │
    ▼
CI（ci.yml）── 失败 ──✗ 整条链路终止，GHCR 无新镜像
    │ success
    ▼（workflow_run 串行门禁，见文档 15）
Docker Images（docker.yml）
    ├── build-push × 4（matrix 并行）── sha-<短哈希> + latest 两个 tag 推 GHCR
    │ success
    ▼（needs: build-push）
deploy job
    ├── SSH: git pull --ff-only → compose pull → up -d → image prune
    └── Smoke check: 轮询网关登录接口，拿到标准 400 业务响应即判定链路就绪
```

串行有两层保障：`workflow_run` 保证 CI 绿才构建；`concurrency: production-deploy`
（`cancel-in-progress: false`）保证两次 push 的部署排队执行，不交叉重建容器。

### 1.2 deploy job 的两个 SSH step

`docker.yml` 中 deploy job 拆成两个 step，复用同一对服务器专用密钥：

| step | 职责 | 关键参数 |
|---|---|---|
| Deploy to production server | 拉代码、拉镜像、滚动重建容器 | `command_timeout: 30m`（默认 10m 不够，见踩坑 1） |
| Smoke check | 容器状态确认 + 登录链路轮询探活 | 轮询 24 × 5s = 2 分钟上限 |

部署脚本（在服务器上执行）：

```bash
set -e
cd /opt/mall/app
git pull --ff-only                                      # 只拿最新 compose / 种子文件（.env 不在 git，不受影响）
docker compose -f deploy/docker-compose.prod.yml pull   # 分层增量拉取（见 1.4）
docker compose -f deploy/docker-compose.prod.yml up -d  # 有新镜像的容器重建，其余不动
docker image prune -f                                   # 清理换下来的旧层
```

冒烟检查故意用**错误密码**登录：期望拿到 `{"code":400,"message":"用户名或密码错误"}`。
这个设计一次验证了 网关路由 → user-service → DB/Redis 链路 + 统一响应体格式，
且不依赖任何测试账号（真实凭证不入流水线）。

### 1.3 服务器侧前置准备（一次性）

流水线脚本的前提是服务器上已存在一个"可部署"的仓库工作区——首次部署前手动做一次：

```bash
# 1. clone 仓库到固定目录（deploy job 的脚本写死 cd /opt/mall/app）
git clone https://github.com/jsdawn/springLearningProject.git /opt/mall/app
cd /opt/mall/app

# 2. 配置部署密钥：compose 中所有 ${VAR:?} 强制注入的密钥都从这里取
cp deploy/.env.example deploy/.env
nano deploy/.env   # 填入 MYSQL_ROOT_PASSWORD、JWT_SECRET 等真实值（.env 被 gitignore，只存在于服务器）

# 3. 登录 GHCR：镜像包默认继承仓库可见性，docker pull 匿名只对 public 包生效；
#    用 PAT（read:packages）登录一次，凭证由 docker-credentials-store 保存
docker login ghcr.io -u jsdawn -p <ghp_xxx>

# 4. 生成流水线专用密钥对（不做它用）
ssh-keygen -t ed25519 -f ~/.ssh/github_deploy -N ""
cat ~/.ssh/github_deploy.pub >> ~/.ssh/authorized_keys

# 5. GitHub 仓库 Settings → Secrets and variables → Actions 添加三个 repository secret
#    SSH_HOST          = 服务器公网 IP
#    SSH_USER          = ubuntu
#    SSH_PRIVATE_KEY   = ~/.ssh/github_deploy 私钥全文（含 BEGIN/END 行）
```

部署账号必须能免 sudo 操作 docker（`sudo usermod -aG docker ubuntu` 后重新登录生效）。

流水线侧对工作区有两个隐含假设，破坏了 `git pull --ff-only` 会直接失败：
分支必须跟踪 origin/main 且无本地改动（服务器上别手动改文件）；
`.env` 不在 git 中，`git pull` 永远不会碰它。

### 1.4 分层镜像 + 可复现构建：部署拉取量的优化闭环

生产在 4Mbps 小水管上，部署耗时完全取决于"每次要拉多少层"。两个 commit 构成组合拳：

**第一层：layertools 分层 jar（`47a63d6`）**。四个 `.docker/Dockerfile.*` 在 build 阶段
`java -Djarmode=layertools extract` 把 boot jar 拆成四层，运行阶段分层 COPY：

| 层 | 内容 | 变化频率 |
|---|---|---|
| dependencies | 所有第三方依赖 jar | 依赖不变就不变 |
| snapshot-dependencies | 内部模块（common-core 等 SNAPSHOT） | 内部代码变才变 |
| spring-boot-loader | 启动器 | 几乎不变 |
| application | 业务 classes | 每次代码变更 |

启动入口相应改为 `java $JAVA_OPTS org.springframework.boot.loader.JarLauncher`。

**第二层：可复现构建（`b0e9b2c`）**。Maven 默认把"构建时刻"写进每个 jar entry 的 mtime，
导致即使依赖零变化，每次构建的 jar 字节都不同 → dependencies 层 digest 每次全变 →
分层承诺落空，服务器每次仍全量重拉 ~200MB。修复只需父 pom properties 一行：

```xml
<project.build.outputTimestamp>1760000000</project.build.outputTimestamp>
```

- Boot 2.7 的 spring-boot-maven-plugin **没有** `reproducible` 参数（3.x 才有）；
  它靠 repackage goal 的 `outputTimestamp` 参数（since 2.3.0）default-value
  自动绑定 `${project.build.outputTimestamp}`，maven-jar-plugin 3.2.0+ 同样识别该属性，
  所以 properties 一行同时覆盖 boot jar 与内部模块原始 jar。
- 副作用：jar 内不再有构建时间信息。项目镜像追溯走 GHCR `sha-<commit>` tag，
  不受影响。

时间账（4Mbps ≈ 0.5MB/s）：~200MB 全量 ≈ 7 分钟起步、拥塞期直接超时；
稳态只拉 MB 级 application 层 ≈ 几十秒。**注意：可复现构建上线后的第一次构建
依赖层 digest 仍会变一次（固定时间戳 ≠ 历史实时时间戳），是"最后一次全量"，
此后层进入冻结状态。**

## 二、使用步骤

日常发布就是三件事：

```bash
git add ... && git commit -m "..." && git push   # 之后全自动：CI → 镜像 → 部署 → 冒烟
```

- 观察进度：GitHub 仓库 Actions 页；deploy 全绿即生产已运行新版本。
- **回滚**：生产 `docker compose -f deploy/docker-compose.prod.yml` 手动把
  compose 里 image tag 换成历史 `sha-<commit>` 后 `up -d`（也可临时
  `docker tag` 后拉起）。自动回滚不在当前链路内。
- 服务器上手动重跑部署：`cd /opt/mall/app && git pull --ff-only` 后重跑上面
  1.2 节的四条命令即可，与流水线行为一致。

## 三、踩坑记录

1. **appleboy/ssh-action 默认 10 分钟超时**。GHCR 拉取抖动时 `compose pull` 直接
   Run Command Timeout，job 失败但部署可能半途而废。`command_timeout: 30m` 兜底。
2. **非 reproducible 构建让依赖层 digest 每次全变**（本阶段核心坑）。现象：服务器日志
   大量层重新 Downloading（45~90MB 级），上次"分层很省"的承诺完全没兑现。根因：
   Maven 打包默认写入实时时间戳 → jar 字节漂移 → 层 digest 变。见 1.4 节修复。
   **排障入口：看 deploy 日志里 `Already exists` 与 `Downloading` 的比例**——
   前者多才是分层在生效。
3. **up -d 后立即 curl 会误报**。Spring Boot 就绪要 30~65 秒，期间连接被重置
   （curl exit 56），旧版冒烟把它当部署失败。改为轮询：最多 24 轮 × 5s，
   拿到 `"code":400` 即过。实测就绪窗口 ~65 秒（attempt 13）。
4. **GHA runner 无状态，BuildKit 缓存不保证命中**。`cache-from/to: type=gha` 有
   LRU 淘汰，runner 换机器时构建期拉基础镜像也慢；这是构建慢、部署慢两条链路
   要分开看的原因。
5. **deploy 触发的腾讯云异地登录告警属正常**。GitHub Actions runner 是美国 Azure IP，
   SSH 登录会触发告警，与本地 Clash 代理无关；流水线专用密钥单独成对，便于审计与吊销。
6. **concurrency 必须配在 job 级且不可取消**。`cancel-in-progress: false` 让后到的
   部署排队——若允许取消，先发的部署可能被半途砍掉，容器停在中间状态。

## 四、与规范 CD 的差距（当前边界）

16 号文档差距表中"部署触发 / 密钥管理"两项已由本阶段补齐，剩余边界：

| 要素 | 当前状态 | 规范做法 |
|---|---|---|
| 环境分层 | 测试（compose.ghcr）+ 生产（compose.prod）两套，同一 `sha-xxx` 晋升 | 测试环境自动化验收后再晋升 |
| 数据库变更 | 迁移脚本手动执行 | Flyway/Liquibase 纳入发布流程 |
| 发布策略 | 全量替换（停机数秒） | 滚动 / 蓝绿 / 金丝雀 + 健康检查 |
| 回滚 | 手动换 sha tag | 一键回滚到上一成功版本 |
| 通知 | 无 | 部署结果推送（IM / 邮件） |
